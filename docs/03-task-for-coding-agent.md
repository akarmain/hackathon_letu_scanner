# Задание ИИ-агенту: ревью и доработка MVP

Скопировать этот текст в отдельную задачу агенту после того, как команда проверит и при необходимости поправит `docs/01-mini-tz-mvp.md`.

---

Ты работаешь в Android-проекте `hackathon_letu_scanner`. Цель — довести существующий Java Android MVP до демонстрационного состояния по документу `docs/01-mini-tz-mvp.md`. Прежде чем менять код, прочитай полностью:

1. `AGENTS.md`;
2. `docs/01-mini-tz-mvp.md`;
3. `docs/02-demo-data-and-presentation.md`;
4. текущие `README.md`, `schema.dbml`, Gradle-файлы и существующий код.

## Результат, который требуется

Сделай офлайн-прототип ТСД с тремя работающими операциями: приёмка, размещение, пополнение; сканированием EAN-13 камерой; локальными тестовыми данными; экраном остатков товара по ячейкам. Приложение должно собираться и быть пригодным для двухминутной демонстрации.

## Правила работы

- Сначала выдай краткий аудит: что уже соответствует ТЗ, чего не хватает, какие изменения планируешь. Затем приступай к реализации.
- Не удаляй пользовательские изменения и не делай `git reset --hard`/`git checkout --`.
- Сохраняй Java и Android Views. Не переписывай приложение на Kotlin/Compose.
- Минимальная поддерживаемая версия — Android 8 (API 26); ориентир кейса — Android 14 (targetSdk 34). Если текущая конфигурация новее, не понижай её без причины.
- Весь основной путь обязан работать без интернета. Не используй удалённые изображения и сетевые API.
- Камера — единственный штатный ввод кода. При необходимости допустим явно маркированный скрытый демо-режим, но не заменяй им камеру.
- Обрабатывай только EAN-13, корректно обрабатывай отказ в разрешении камеры и неизвестный/неподходящий товар.
- После сканирования обязательно требуй явного подтверждения перед изменением данных.
- Не связывай Activities или бизнес-логику напрямую с ML Kit: сохраняй/выдели контракт `BarcodeScanner`, нейтральный `ScanResult` и реализацию ML Kit. Архитектура должна позволять добавить DataWedge без изменения операций.
- Предпочти законченную вертикальную демо-ветку сложным, но недоделанным функциям.

## Обязательная последовательность

1. Сверь текущие экраны/модели с ТЗ и используй существующий код там, где он подходит.
2. Добавь недостающие зависимости CameraX и bundled ML Kit Barcode Scanning. Не используй unbundled-модель, которой нужна сеть.
3. Приведи seed-данные и задания к единому сценарию из `docs/02-demo-data-and-presentation.md`. Указанные EAN-13 уже валидны; если их меняешь, пересчитай контрольные цифры и синхронно обнови seed-данные, документацию, этикетки и README.
4. Сделай так, чтобы подтверждённые операции меняли локальные остатки и повторное открытие отчёта показывало изменения. Для MVP допустим repository в памяти только если он переживает поворот экрана; предпочтителен Room, так как ТЗ требует данные на устройстве после перезапуска.
5. Сделай крупный ТСД-интерфейс, понятные статусы, звук/вибрацию, пустые/ошибочные состояния.
6. Добавь/обнови README: запуск, разрешение камеры, тестовые штрихкоды, архитектура, сценарий демонстрации.
7. Напиши unit-тесты для как минимум: валидации формата EAN-13, запрета операции с неподходящим товаром и перемещения остатка между ячейками.
8. Запусти `./gradlew test` и `./gradlew assembleDebug`. Исправь ошибки в изменённом коде. В конце укажи выполненные проверки и всё, что нельзя проверить без устройства.

## Критерии «готово»

- Все четыре операции открываются с готовыми заданиями и приводят к наблюдаемому результату.
- Сканирование EAN-13 камерой использует ML Kit офлайн.
- Ошибочные сценарии не изменяют остатки.
- Экран «Остатки» показывает итоговое количество товара и список ячеек.
- Демо не требует сети, логина или внешнего сервиса.
- Проект успешно собирается в debug-вариант.
- В финальном отчёте перечисли: изменённые файлы, как запустить демо, тестовые штрихкоды, результаты команд и известные ограничения.
